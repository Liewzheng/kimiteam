# 团队冷启动 (team-onboarding)

当用户开启团队模式但没有任何团队成员时，或者用户主动表达「组建团队」「创建初始团队」「我要一个团队」等意愿时，执行此 onboarding 流程。

## 触发条件

1. **自动触发**：用户开启 `/team on` 且用户级 `~/.kimi-code/agents/` 目录中没有任何 `.md` 配置文件。已有任一 profile 时**不主动触发**。
2. **用户主动**：用户说出「组建团队」「创建初始团队」「我要一个团队」「帮我把团队建起来」等类似表达。已有成员时也响应用户明说的重组要求。

## 核心流程

### 第一步：说明意图

向用户简要说明 onboarding 流程：

> 我来帮你组建初始团队！请回答 4 个问题，我会根据你的需求匹配合适的成员角色，然后逐一创建。整个过程大约需要 1~2 分钟。

### 第二步：一问一答（固定 4 题，不得超过 6 题）

**使用 `AskUserQuestion` 工具一次调用携带全部 4 题，一轮问完（该工具支持一次 1~4 题）。** 用户可选多项（Q1/Q2）或单项（Q3/Q4）。只有用户选了 Other 需补充时才追加一轮澄清。

#### Q1 主要使用场景（多选）

```
选项：
a) 编程开发
b) 写作·内容创作
c) 学习·研究·知识整理
d) 数据·表格·分析
e) 项目·产品·管理文书
f) 生活与日常自动化
```

#### Q2 主要让它做什么（多选）

```
选项：
a) 从零做新东西
b) 修改完善已有的
c) 阅读·总结·整理资料
d) 检查把关·评审提意见
e) 写文档报告
f) 重复劳动自动化
```

#### Q3 模型成本策略（单选）

```
选项：
a) 尽量省钱全本地（所有成员用本地模型）
b) 性价比均衡（只读岗用本地 + 干活岗用便宜在线模型，推荐）
c) 质量优先（核心岗用最强模型）
```

#### Q4 团队规模（单选）

```
选项：
a) 精简 3~4 人
b) 标准 5~7 人
c) 全编制 8 人以上
```

### 第三步：选项→岗位方向映射规则

以下为角色映射指南，**不是穷举清单**，允许你根据用户的其他补充自由发挥，但要保持中性专业人设。

#### Q1 场景映射

| 场景 | 建议角色方向 |
|------|-------------|
| 编程开发 | 按技术栈配工程师（前端/后端/嵌入式/全栈）+ 代码探索员 + 质量评审员 |
| 写作·内容创作 | 撰稿员 + 校对润色员 + 资料研究员 |
| 学习·研究·知识整理 | 研读员 + 笔记整理员 + 知识库管理员 |
| 数据·表格·分析 | 数据处理员 + 可视化分析师 |
| 项目·产品·管理文书 | 需求梳理员 + 文档工程师 + 进度记录员 |
| 生活与日常自动化 | 脚本工程师 + 流程调试员 |

#### Q2 决定职能岗增减

- 包含「检查把关·评审提意见」→ 增加一名「把关/评审员」
- 包含「写文档报告」→ 增加一名「文档工程师」
- 包含「阅读·总结·整理资料」→ 增加一名「研究员」或「资料整理员」
- 包含「重复劳动自动化」→ 增加一名「自动化工程师」

#### Q3 模型成本策略

先读取用户 `config.toml` 的 `[models]` 节，找出其中属于本地模型的 id（通常以 `local/` 前缀，如 `local/gemma4-26b`）。记作 `${localModelId}`；若 `[models]` 中没有本地模型，记作 `null`。

| 选项 | model_preference 值 |
|------|-------------------|
| a) 尽量省钱全本地 | 所有成员填 `${localModelId}`；若 `${localModelId}` 为 `null`，全部回退 `secondary` 并在收尾告知用户（「未检测到本地模型，已改用性价比方案」） |
| b) 性价比均衡 | 只读/整理岗填 `${localModelId}`，干活/创作岗填 `secondary`（由 `[secondary_model]` 指向便宜在线模型）。推荐。若无本地模型，全填 `secondary` |
| c) 质量优先 | 核心岗 `primary`，辅助岗 `secondary` |

#### Q4 截断团队人数

- a) 精简 → 最多选 4 人
- b) 标准 → 最多选 7 人
- c) 全编制 → 8 人以上，按需

### 第四步：逐个建档

使用 `TeamHire` 工具为每个成员创建配置文件。要求：

1. **scope** 固定为 `user`
2. **name** 使用 kebab-case（如 `frontend-engineer`、`content-writer`）
3. 以下字段必须齐全：
   - `role` — 岗位名称（中文，如「前端工程师」）
   - `description` — 一句话介绍（中文）
   - `when_to_use` — 何时派给此成员（中文）
   - `prompt` — 系统提示词（中文，具体说明职责、工作方式、输出规范）
   - `tools` — 该成员可用的工具列表（根据角色合理分配）
4. **人设要求**：所有成员保持 **中性专业人设**，禁止照搬或模仿任何现成团队（如 KB、Kimi、Claude 等产品）的人格设定。使用客观、职业化的描述。

#### prompt 编写指南

- 明确该角色的核心职责和决策边界
- 说明工作流程：接收任务→分析→执行→报告
- 指定输出规范：格式、详细程度、引用要求
- 说明协作方式：何时需要请示主 agent、何时可以独立决策
- 如有工具限制，需说明工具使用规则

### 第五步：收尾

1. 所有成员创建完成后，**在回复里用表格输出最终名单**（名字 / 职位 / 模型），并提示用户可输入 `/team` 查看面板
2. 向用户交代三条制度：
   - **最小可验证任务**：每次派工都是一个可以独立验证的最小任务，不一次性丢大需求
   - **完工必验收再计分**：每个任务完成后你必须评审验收，合格才计入绩效
   - **评分影响后续派工**：成员的评分会影响后续任务分配和模型搭配——高分成员优先派关键任务

### 幂等与回退

- 如果用户拒绝回答问题（关闭 `AskUserQuestion` 或不作答），**当次流程放弃**，不重复追问，不生成任何成员
- 如果 `TeamHire` 某个成员失败（例如工具调用返回错误），**如实报告该成员创建失败**，继续处理其余成员，不假装成功
- 已有成员时（除非用户明确要求重组），不执行此流程
